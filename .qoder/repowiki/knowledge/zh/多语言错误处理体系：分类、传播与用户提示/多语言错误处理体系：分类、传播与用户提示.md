本仓库在 Next.js 应用层与 Go Worker 服务中分别建立了结构化的错误处理方案，覆盖数据库异常分类、加密配置校验、外部 API 错误包装、后台任务 panic 恢复等关键场景。

## 一、Next.js 应用层（TypeScript）

### 1. 数据库错误分类器
- `src/server/db/errors.ts` 提供 `classifyDatabaseError(error)`，将 Prisma/Postgres 的原始错误码映射为统一的结构化对象 `{ code, message, status }`。当前已识别 P2021/P2022/42703/22P02/42704/42883/0A000 等代码，统一返回 `DATABASE_SCHEMA_OUT_OF_SYNC` + HTTP 503，并附带运行迁移的修复指引。

### 2. 加密配置错误检测
- `src/lib/crypto.ts` 在 `getEncryptionKey()` 中校验 `ENCRYPTION_KEY` 环境变量；`isEncryptionConfigError(error)` 通过消息前缀匹配判断是否为配置缺失。该函数被多个 Route Handler 复用（chat、fortune、images、keys），在 catch 分支中返回 503 + 明确的用户操作指引。

### 3. Route Handler 的统一 try/catch 模式
- 每个 API route 使用 try/catch 包裹，按优先级处理：
  1) `classifyDatabaseError` → 503 + 结构化 JSON
  2) `isEncryptionConfigError` → 503 + 配置提示
  3) 兜底 → 500 + `{ error, code: "CHAT_REQUEST_FAILED", details, stack }`
- 鉴权失败直接返回 `new Response("Unauthorized", { status: 401 })`，参数校验失败返回 400。

### 4. 业务错误类型
- `src/lib/fortune/api-errors.ts` 封装命理子系统的错误转换逻辑，同样复用 `isEncryptionConfigError` 做前置拦截。

## 二、Go Worker 服务

### 1. 错误构造与重试判定
- 各执行器使用 `fmt.Errorf(...)` 构造带上下文的错误字符串，如图片生成接口包装 status/type/message 三元组。
- `shouldRetryImageEdit(err)` 基于错误消息关键字（"context deadline exceeded"、"status=502"、"type=upstream_error" 等）判定是否可重试。

### 2. Panic 恢复机制
- `worker/internal/dispatcher/dispatcher.go` 在 goroutine 级别使用 defer + recover() 捕获执行器内部 panic，记录日志并通过 `reporter.ReportFailed` 上报失败状态，防止单条任务崩溃拖垮整个 Worker。

### 3. 配置错误
- `worker/internal/crypto/aes.go` 对 ENCRYPTION_KEY 长度、IV 格式等进行严格校验，失败时返回明确的中文错误信息（如“解密参数不可为空”、“密文已被篡改或密钥错误”）。

## 三、跨层约定

| 维度 | 约定 |
|------|------|
| 错误分类 | 数据库错误 → 专用分类器；加密配置 → 专用检测器；其他 → 通用 500 |
| 响应格式 | 成功走 Response.json(data)；错误走 { error, code?, details? } JSON |
| HTTP 状态码 | 401 未授权 / 400 参数错误 / 404 资源不存在 / 503 配置或架构不一致 / 500 未知异常 |
| 日志 | 所有 catch 分支均 console.error / slog.Error 输出完整堆栈 |
| 用户提示 | 503 类错误附带可操作的修复说明（如设置 ENCRYPTION_KEY、运行 Prisma db push） |

## 四、开发者应遵循的规则

1. 不要在 Route Handler 内裸抛 Error — 始终用 try/catch 包裹，让顶层分类器接管。
2. 新增数据库错误码时更新 `classifyDatabaseError` — 保持 503 语义一致。
3. 涉及 API Key 解密的调用必须用 `isEncryptionConfigError` 检查 — 避免把配置问题暴露为 500。
4. Go 执行器不要 panic — 如需防御性编程，请在 goroutine 外层加 recover，并在错误消息中包含可重试关键词以便上层判定。
5. 对外错误消息面向用户 — 不要泄露内部堆栈或敏感字段，必要时保留 details 仅用于调试日志。
